- [01 のノートブック](../notebooks/01_titanic_first_submission.ipynb)で、データ確認 → EDA → 前処理 → ランダムフォレスト → 交差検証 → 提出

### 結果

| 評価のしかた | スコア |
|---|---|

### 学んだこと

1. **コードはエージェントが書く。人間の仕事は評価を正しく組み、結果を疑って判断すること**
2. **学習に使ったデータで測った数字は信用しない**。モデルは丸暗記できる（過学習）。98% と 82% の差がその証拠
3. **交差検証（CV）**：train を5つに分け、「4つで学習 → 残り1つで採点」を5回繰り返す。採点するデータはそのモデルの学習に使っていないので、本当の実力に近い
4. **ベースラインを先に決める**。「女性なら生存」だけで約79%当たる。これを超えないモデルには意味がない
5. **前処理の値（中央値など）は train だけから決める**。test の情報を使うとリークになる
6. **CV と LB はずれることがある**。今回は CV 0.818 に対して LB 0.754 で、性別ルールにも負けた
   - Public LB は約200人分しかなく、1人で約0.5%動く。もともとブレが大きい
   - 深さ無制限のランダムフォレストが、運賃や年齢の細かい値を丸暗記している可能性
7. **LB を上げること自体を目的にしない**。LB を見ながら調整すると、LB の200人に過学習する。CV を信じ、LB は大きなずれの確認に使う
8. **提出前のチェック**：行数（418）、列名（`PassengerId, Survived`）、予測の生存率が train の生存率（38%）から大きく外れていないか

### 覚えた言葉

| 言葉 | 意味 |
|---|---|
| 特徴量 / 目的変数 | 予測に使う列 / 当てたい列（`X` / `y`） |
| 欠損値 | 空欄。埋めるか、その列を使わない |
| EDA | モデルを作る前にデータを眺めて傾向をつかむこと |
| ワンホットエンコーディング | C/Q/S のようなカテゴリを「その値か？」の 0/1 の列に分けること |
| ベースライン | 一番単純な方法のスコア |
| 過学習 | 学習データを丸暗記して、未知のデータに弱くなる状態 |
| 交差検証（CV） | 学習に使っていないデータで採点を繰り返す評価方法 |
| リーク | 本番では使えない情報が学習や評価に紛れ込むこと |
| Public LB | Kaggle の順位表のスコア。test の一部（Titanic では約半分）で計算される |
